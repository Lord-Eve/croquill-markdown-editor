## 1. 目标

Claude 在 2026-11-18 实测了 `main`（施工单 06 合并后）。环境是本机 headless Edge，视口 1200 × 850，加载真实 `main.ts` 应用。样本有两份：私人样本 105 KB，以及把它复制 4 份、用空行连起来的 420 KB 文本。

| 动作 | 105 KB | 420 KB |
| --- | ---: | ---: |
| 打开（`surface.load` 到两帧之后，不含程序启动） | 1.2 秒 | 3.8 秒 |
| 每次按键（keydown 到下一帧） | 中位 10 毫秒 | 中位 48 毫秒 |
| 停手后整理一次（主线程长任务） | 0.19–0.23 秒 | 0.87–1.0 秒 |
| 保存前强制整理（`getMarkdown()`） | 0.23 秒 | 1.0 秒 |
| 切到源码 / 切回所见即所得 | 0.21 / 0.17 秒 | 0.66 / 0.71 秒 |

CPU 剖析结论：

1. **停手整理和保存。** ProseMirror 写回 Markdown 本身只占约 10%（105 KB 时约 22 毫秒）。其余几乎全是 remark 对全文的重复解析，一次整理约十来遍：`preserveTableSource`、`preserveRenderedSource`、`preserveEmptyListSource` 各自把原文和新文各解析一遍，改完再解析一遍核对；`serializeRichDocument` 对“上次保存的文本”和“打开时的原文”各跑一轮；`preserveInlineEdit` 里的 `hasEquivalentMarkdownStructure` 又解析两遍。而“打开时的原文”在两次打开之间不变，每次整理都被重新解析。
2. **打开。** `ensureRich()` 约占打开时间的六成。其中整理一遍加 `hasEquivalentMarkdownStructure` 结构核对约 0.47 秒，`preservedMarkdownBlocks` 约 0.16 秒，都是全文解析。
3. **每次按键。** `onEdit` → `outlineController.notifyDocumentEdited()` → `syncNow()` → `getOutlineHeadingBoxes()`：每次按键都遍历全文、对**每个**标题调用 `nodeDOM` 和 `getBoundingClientRect`。420 KB 样本有 560 个标题，这一项每键约 8 毫秒。
4. **停手之后。** 字数统计 `markdownForWordCount()` 和大纲 `markdownOutline()` 各解析一次全文，约 0.2 秒（105 KB）。

做完后：

| 动作 | 105 KB | 420 KB |
| --- | ---: | ---: |
| 停手整理 / 保存前强制整理（只改了一两段时） | ≤ 50 毫秒 | ≤ 150 毫秒 |
| 打开 | ≤ 0.6 秒 | ≤ 2 秒 |
| 每次按键 | 中位 ≤ 10 毫秒 | 中位 ≤ 20 毫秒 |

切换模式不设单独目标，随 A、C 变快即可，但不得变慢。保存结果的正确性优先于以上所有数字：哪一项达不到目标，就如实写进 PR 说明，**不要为了达标放宽任何保真规则**。

## 4. 设计

### A. 每份文本只解析一次

- 提供一个共用的 Markdown 解析入口，例如在 `fidelity.ts` 导出 `parseMarkdownAst(text)`，内部按文本内容缓存最近几次的结果。`table-source.ts`、`rendered-source.ts`、`empty-list.ts`、`fidelity.ts` 里的全文解析都改用它。
- 所有使用方**不得修改**拿到的语法树。测试里要对共享的树做冻结或前后比较，来证明这一点。
- 打开时的原文（`richOriginText`）解析一次后一直复用，到下次打开或重建所见即所得才换。
- 解析配置（remark 插件组合）必须和现在完全相同。
- 只做 A 时，所有现有测试的输出逐字节不变。

### B. 只整理改动的那几段

整理时先比较 `richSnapshot` 和当前文档，找出变动的顶层块范围。下列条件**全部满足**才走局部整理，否则走现在的全文整理：

1. 维护着一张“顶层块 → 上次已发布文本 `this.raw` 中的字节范围”的对应表，并且和 `richSnapshot` 的顶层子节点一一对应。表在全文整理或打开后建立；局部整理后，改动处之后的范围按长度差平移，新块的范围取自局部解析结果。对不上就作废，下一次走全文并重建。
2. `richContextVersion` 没有变化（查找替换等操作没有切换文本上下文），也没有命中 `richExactSources`。
3. 变动范围内、以及紧挨它前后的块，不是 front matter、`[TOC]`、原文块（`croquill_raw_block`）、HTML 块、脚注定义或引用式链接定义。整篇文档里有引用式链接定义或脚注定义时，改动的块里不得出现对应的引用写法。
4. 下面的局部核对通过。

局部整理的做法：

- 只把变动的顶层块序列化成 Markdown。序列化器、`inlineRaw.serialize`、`guardLineStart` 的规则必须和全文整理相同。
- 对这几块的原文片段和新片段，跑与全文整理相同的保留步骤（表格、空列表项、渲染源码、行内 HTML / 普通扩展写法的行内映射）。
- 用新片段替换 `this.raw` 中这几块原来的字节，块与块之间的原有空白不动。

局部核对：把“前一块 + 新片段 + 后一块”连同原有分隔空白拿出来单独解析，要求同时满足：

- 前后两块的结构与原来相同；
- 新片段解析出的顶层块数和结构，与 ProseMirror 里变动后的块一致（与全文整理用的结构比较规则相同）；
- 没有和前后块合并、吞并或拆开，例如段落变成列表的懒续行、Setext 下划线、表格续行。

任一条件不满足，就丢弃局部结果，走全文整理，并重建对应表。

其他要求：

- 局部整理不碰 ProseMirror 的文档和撤销历史，只改 `this.raw` 和相关快照。
- 组词期间不整理，保存、切换模式、关闭确认前的强制整理照旧（这些路径同样可以走局部）。
- 留一个只在测试里用的开关，可以强制走全文整理，便于对比。不要做成界面选项或配置项。

### C. 打开时复用解析结果

`ensureRich()` 里的整理和 `hasEquivalentMarkdownStructure` 结构核对，使用 A 的缓存，不重复解析同一文本。`preservedMarkdownBlocks()` 解析过的原文也复用。打开后建立 B 的对应表时，也尽量复用这次解析。

### D. 按键时的大纲和停手后的统计

- 大纲跟随在按键时不得逐个测量全部标题。可以只在视口附近查找：利用标题在文档里按顺序排列的特点二分查找；也可以缓存标题元素列表，只在标题增删时重建。要求每次按键的耗时不随标题总数线性增长。
- 大纲跟随的现有行为不变：当前标题高亮、折叠后高亮父级、点击跳转后的固定、滚动时更新。现有大纲测试全部照旧通过。
- `updateStats()` 里的字数统计和大纲重建，对同一份文本只解析一次，用 A 的缓存即可。

### E. 测速脚本

- 新增一个手动运行的测速脚本，例如 `npm run perf`，不放进 `npm test`，也不进 CI。量第 1 节表格里的五项，打印成表格。
- 样本：`examples/private/` 下有 `.md` 时，用第一份私人样本（×1 和 ×4）；同时总是另测一份由公开 `examples/*.md` 拼接生成的约 100 KB 和约 400 KB 文本，保证没有私人样本的机器也能复现。
- 脚本可以在本机读取私人样本来测量，但**不得打印、记录或提交私人样本的任何内容**，包括文件名和段落文字。输出里只出现字节数、行数和耗时。
- 每项量多次取中位数，按键至少 12 次。

## 5. 测试要求

用仓库现有的单元测试和浏览器应用测试写法。

至少覆盖：

1. **局部与全文一致**（B 的主要保证）：以所有公开 `examples/*.md` 和 `tests/fixtures/fidelity-samples.ts` 的样本为底，在开头、中间、末尾，以及表格、列表、引用、标题、含行内 HTML 和双链的段落里，各做下面几种改动：
   - 输入一个字；
   - 删除一个字；
   - 回车拆段；
   - Backspace 并段；
   - 把段落改成标题；
   - 粘贴一段多行文字。

   每次分别用局部整理和强制全文整理得到结果，要求两者结构等价，未改动的顶层块逐字节保持原文。对两者逐字节不同的情形，在 PR 说明里列出样本和原因。
2. **退回全文**：第 4 节 B 的每个条件，各至少一例，证明会走全文整理，结果正确。例子包括：改动紧挨原文块；文档有 `[a]: url` 定义且改动处写了 `[a]`；把段落改成以 `- ` 开头的文字，紧接在列表后；在表格下一行输入 `|`；front matter 后第一段。
3. **连续编辑**：同一文档里连续做 50 次随机位置的局部编辑（固定随机种子），每次整理后都和强制全文整理的结果比较，对应表不得错位。
4. **组词与撤销**：模拟组词期间不整理；组词上屏后局部整理正确；局部整理之后撤销、重做，保存结果与全文整理一致。
5. **打开不改字**：所有公开样本打开后不编辑，保存逐字节一致（现有测试已覆盖，必须照旧通过）。
6. **语法树不被改动**：A 的共享语法树被各步骤使用后，内容与使用前完全相同。
7. **大纲**：现有大纲跟随测试全部通过；再加一个测试，证明按键时测量的标题数量不随标题总数增长（例如统计 `getBoundingClientRect` 调用次数）。

性能数字不写成测试断言（机器负载会让测试时好时坏），只在测速脚本里量。

真实窗口和真实拼音输入法的验收由 Claude 在合并前做：打开私人样本和它的 4 倍文本，在文中段落连续用拼音输入，停手后立即 Ctrl+S，与原文逐字节比较；并用本机官方 Typora 打开同样的文件对照手感。
